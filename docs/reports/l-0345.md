## The finding: checkpoint selection is ~11x noise-dominated

`wp-l.md` describes L4 as switching selection *from clean val loss to degraded val loss*. **That is not what the
code does.** `train.py` already passes the training `degradation` object to `validate_epoch`, and
`Degradation.forward` dispatches on `severity` (None) rather than on `.eval()`, so validation already runs under
the training generator — but **with a fresh random corruption every epoch**. Epoch-to-epoch val losses are
therefore computed on *different corruptions*.

Measured on the champion's own trained weights (`rt_d_pma0_aug_meanpt_encoder_20260903_221125.pth`, 2000 val
events, 8 corruption draws, weights frozen):

```
val loss over 8 draws, FIXED weights:  mean 0.907366  std 0.005896  spread 0.019562
val AUC:                               mean 0.9157    std 0.0021
```

Against the champion's own training log, its last twelve epochs:

| epoch | 20 | 21 | 22 | 23 | 24 | 25 |
|---|---|---|---|---|---|---|
| val loss | 1.041768 | 1.051330 | 1.042153 | **1.041679** | 1.043764 | **1.041243** ← selected |

**The best three epochs span 0.000525; the corruption draw alone moves val loss by std 0.005896 — 11x larger.**
So among near-tied epochs the champion's checkpoint selection is choosing the epoch that drew the easiest
corruption, not the best model. That is the real content of L4, and it is a defect in the champion's training
procedure rather than a preference between two criteria.

`val_degradation_seed` (default `null` = champion behaviour) seeds the RNG immediately before the validation
pass and restores the previous RNG state immediately after, so the corruption is identical every epoch and the
*training* stream is unperturbed.

`0.755/epoch` = `0.999**281`, i.e. the per-step 0.999 the package asks for, expressed per epoch. Per-*step* EMA

## A second defect, found and fixed before it ran

My first EMA averaged parameters **and** buffers. BatchNorm running statistics are buffers and are already an
EMA of their own, so averaging them again only adds lag — and for the *preprocessor's* BatchNorm it is strictly
wrong, because those statistics describe the input data and depend on no weight at all. Measured on a 2-epoch
smoke: averaging buffers moved `preproc.batch_norm.running_var` by **8.36e4 on a raw magnitude of 9.34e5 (9%)**,
a shift in the input normalisation that has nothing to do with the averaging being tested. The learnable
weights moved by ≤5.5e-3. Now: parameters averaged, buffers copied from the latest epoch. Verified — buffer
diff exactly 0.0, parameter diff 5.5e-3.

Known approximation, recorded: a textbook SWA would *recompute* the activation BatchNorm statistics under the
averaged weights (`swa_utils.update_bn`). Copying the final epoch's is cheaper and is what L3 does.

## Correctness gates (all pass, CPU)

`tests/test_wpl_preprocs.py`:
- **champion `PFPreProcessorMeanPt` is bit-exact after the hook refactor — max diff 0.0.** Non-negotiable, since
  both new arms subclass it.
- L1: `num_features` 15, BatchNorm rebuilt to 6 channels, channels 2/3 are sin/cos φ, sin²+cos² = 1.
- L2: dxysig channel bounded at 1.000; `num_features` unchanged.
- each arm changes only its own channels — every other channel bit-identical to the champion.
- dead candidates stay exactly zero for both arms.
- **all three preprocessors build and run through `eval.py`'s exact path** — fetched by name from the config,
  constructed positionally, encoder sized by `preproc.num_features`, no constructor kwarg anywhere. This is the
  silent-failure class 11 defence and it is why L1 can change the input width safely.

2-epoch CPU `--test_mode` smoke passes for all four arms and the champion control.
