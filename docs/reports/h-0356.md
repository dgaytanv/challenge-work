# WP-H report, 03:56 — scheduler v3 (fair share), H3 done, references 2/3

## Scheduler changes (both planner rulings, both tested, both deployed atomically)

**Atomic replace matters here.** 26 `gpu_slot.sh` processes were live during the last swap. The file
is written to a temp path and `mv`-ed, so running shells keep their original inode. Rewriting in
place truncates the same inode and makes live bash resume mid-token — the campaign-1 hazard.

### Launcher policy (04:00 ruling)
- **Default: a QUEUED job now keeps waiting when its launcher exits.** Detached launches are the norm;
  the old default silently reaped them whenever all five slots were busy.
- `--abandon-if-launcher-dies` restores campaign-1 behaviour.
- `--queue` lists waiting jobs and running slots per package; `--drain <pid|all>` stops waiting jobs.

Test B found a **real bug in the opt-in path**: `setsid` reparents to init before `$PPID` is read, and
`kill -0 1` always fails for a non-root user, so the flag as first written would have abandoned every
detached job instantly — the opposite of its name. It now detects "no launcher to watch" and says so.

### Fair share (04:10 ruling)
When a slot frees, the waiting job whose **package** holds the fewest running slots goes first, ties by
queue time. Each waiter computes this from shared `queue/` and `running/` registries; `flock -n` still
arbitrates, so a race costs ordering, never correctness.

Confirmed in an isolated lock dir (`GPU_SLOT_LOCKDIR` is now overridable for exactly this):
```
[slot 0] released  03:53:58            <- one slot frees
[slot 0] acquired  03:54:01  pkg=pkgB  <- queued 03:53:51, 0 running  -> WINS
[slot 0] acquired  03:54:04  pkg=pkgA  <- queued 03:53:49, 5 running  -> loses despite queueing first
```
I first scored this test as FAILED. That was my error: I took `tail -1` of the log, which was pkgA
acquiring the slot pkgB had *just released*, not the contested one.

**The catch worth carrying:** `torch.load(mmap=True)` returns a **writable copy-on-write** map, not a
read-only one. `clean_data`'s in-place `nan_to_num_` therefore *succeeds* and would privatise all 12 GB
in every process — recreating the problem mmap solves, while looking like it worked. The mapped path
never writes; it verifies in chunks and fails loudly.

`compute_class_weights` returns **ones** unless `class_weights` is set in the data config, and it is not.
So the 4.6× imbalance is currently unweighted, as it was for the champion. That is an arm (WP-L has it),
not a bug.
